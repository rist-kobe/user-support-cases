# 支援事例 No.42

## 種別

性能分析

## 課題・問題点

「富岳」におけるLAMMPSについて
・同様の特性を持つ計算を384 ノード (small)と416ノード(large)で実行したところ、並列数は同程度にも関わらずsmallでの実行がlargeに比べ所要時間が2.0～2.5倍かかってしまう件の調査。
・largeクラスを利用した場合も、同一データであるにも関わらず30%程度の性能差がでることがある。
移植・環境適応

## 分類

性能分析

## 支援内容

１．利用者から提供されたデータに対して、ノード割当ポリシーを変えて性能を測定した。
２．続いて、ノード割当ポリシーの変化で性能が大きく変化したMPI_Allreduce関数について、Intel MPI Benchmark (IMB)で基礎性能を採取した。
３．さらに、MCAパラメータの調整やLAMMPSに搭載されているプロセッサ分割機能を利用し、通信性能の向上が見込まれるかを調査した。

## 支援結果

・まず、smallクラスで実行時間短縮を図るノード割当方法として、3次元形状+トーラス指定を提案した。ただしジョブ実行開始までの時間が長くなることも合わせて報告した (今回の計測の範囲では、3時間のジョブ実行時間指定の場合で2、3日)。よって、計算資源に余裕があるなら、largeクラスの利用を推奨した。また、ジョブ実行までの待ち時間を減らすため、「富岳」ポイントの利用を検討するよう提案した。
・また、IMBのMPI_Allreduceの計測を行い、通信性能とホップ数の関連性を示した。
・最後に、large利用時における性能がブレる現象は再現しなかっため、分析を実施できなかった。今後、通信関連の調査に有効なMPI統計情報を収集するよう依頼者に提案し、MPI統計情報の収集方法も説明した。
